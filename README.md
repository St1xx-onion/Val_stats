# Valorant Stats

Фоновая консольная утилита: сидит и ждёт, пока начнётся матч, и с agent select
держит на экране одну живую таблицу по всем игрокам —
ранг, RR, пиковый ранг, скрытый MMR (куда игрока тянет система), счёт за акт,
винрейт, рейтинг формы, ACS, KAST, HS%,
K/D, damage delta, нож и сколько раз вы с этим человеком уже пересекались.
Когда матч заканчивается — печатает его итоговый счёт и результат каждого.
А в agent select под таблицей подсказывает, кого брать: чего не хватает составу
и на ком из подходящих агентов вы сами играете лучше.

Идея и набор эндпоинтов взяты из открытых проектов
[vRY](https://github.com/zayKenyon/VALORANT-rank-yoinker),
[ValoTrack](https://github.com/kurtxtb/ValoTrack) и
[ValoTracker](https://github.com/Londopy/ValoTracker); код здесь свой и заметно
компактнее.

## Как запустить

Нужен Python 3.10+ (проверено на 3.14).

Просто двойной клик по `run.bat`. Первый запуск сам найдёт Python, создаст
`.venv`, поставит зависимости и сделает `config.json` — примерно минута.

```
run.bat               — рабочий режим, ждёт матч
run.bat test          — самопроверка: контент, lockfile, токены, регион, ваш ранг
run.bat check         — офлайн-тесты разбора, без игры и без сети
run.bat reset         — стереть локальную память матчей и кэш справочников

run.bat who <ник>     — что база помнит об игроке: форма, ранг и матчи ваших встреч
run.bat mates <ник>   — с кем этот игрок сам ходит в очередь, по кэшу
run.bat identify      — назвать тех, кто прятался: все источники сразу, вслух
run.bat match <M12>   — вернуть Riot-идентификатор матча по локальному номеру
run.bat top [n]       — с кем вы чаще всего пересекаетесь
run.bat backfill [n]  — прогреть кэш своей историей, чтобы первое лобби было дешёвым
run.bat agents [n]    — ваш пул агентов: на ком вы играете и как это идёт
run.bat calibration   — по чему сейчас считается счёт 0-1000
run.bat share         — общий пул матчей: что это и сколько ждёт отправки
run.bat share now     — отправить накопившееся в пул (если включено)
run.bat pool          — что скачано из пула и когда обновлялось
run.bat pool sync     — скачать пул сейчас
run.bat update        — проверить GitHub и обновиться
```

Первые четыре команды и `who` / `mates` / `match` / `top` / `calibration`
работают без игры;
в сеть ходят `backfill`, `agents` и `identify`. Первые две — только за вашими
данными (`agents` — чтобы спросить у клиента ваш puuid); `identify` спрашивает
про чужие puuid, которые уже лежат в вашей базе, теми источниками, что включены
в `reveal_sources`.

Окно не закрывается после выхода, так что ошибку видно и при двойном клике.
Если Python не в PATH — скажет об этом прямо, а не мигнёт консолью.

Вручную, без `.bat`:

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python -m valstats.selftest
.venv\Scripts\python -m valstats
```

Порядок: сначала запускаете Riot Client (логин), потом утилиту. Она сама
дождётся клиента, если запустить наоборот, и переподключится, если клиент
перезапустить.

## Что читаем и откуда

**Никакого чтения памяти игры, инжекта DLL, хуков и обхода Vanguard.** Только
HTTP:

| Источник | Что берём |
|---|---|
| `%LOCALAPPDATA%\Riot Games\Riot Client\Config\lockfile` | порт и пароль локального API |
| `https://127.0.0.1:<порт>/entitlements/v1/token` | access token, entitlement, свой PUUID |
| `https://127.0.0.1:<порт>/chat/v4/presences` | `sessionLoopState` — MENUS / PREGAME / INGAME |
| `%LOCALAPPDATA%\VALORANT\Saved\Logs\ShooterGame.log` | регион, шард и строка билда |
| `glz-.../pregame/v1/...`, `.../core-game/v1/...` | состав лобби, агенты, лоадауты |
| `pd.../name-service/v2/players`, `pd.../mmr/v1/players/...` | ники, ранг, RR, история по актам |
| `pd.../match-history/v1/history/...`, `pd.../match-details/v1/matches/...` | ACS, HS%, K/D за последние матчи, агент и карта |
| `pd.../store/v1/entitlements/<свой puuid>/...` | какие агенты у вас открыты (только свой аккаунт) |
| `glz-.../parties/v1/players/<свой puuid>`, `.../parties/v1/parties/<id>` | состав **вашей** пати — Riot отдаёт только её |
| `valorant-api.com` | справочники агентов, рангов, актов, скинов (кэш на сутки) |

Опрашивается только локальный presence раз в секунду. У аккаунта их несколько
(свой presence публикует и сам Riot Client — без состояния сессии), поэтому
берётся именно presence VALORANT. Presence — это удобство, а не гарантия: он
исчезает, когда отваливается чат, и врёт, когда возвращается после
переподключения застрявшим на `MENUS`. Снаружи обе поломки выглядят одинаково —
лобби просто не появляется, — поэтому ни молчанию, ни `MENUS` на слово не
верят: и то и другое перепроверяется у `pregame/core-game` (молчание — не чаще
раза в 5 секунд, `MENUS` — раз в `menus_verify`, по умолчанию 30 с). Если
presence поймали на вранье, дальше ведут игровые серверы — пока presence снова
не начнёт с ними соглашаться. Остальные запросы наружу уходят исключительно в
момент смены состояния: ~12 на само лобби, плюс подгрузка формы (см. ниже).

Есть режим, в котором presence не врёт, а **вообще молчит о состоянии**: в
`skirmish2v2` VALORANT публикует presence, где есть партия и `queueId`, а
`sessionLoopState` нет ни в каком виде (снято с живого клиента посреди матча).
Значит, всю очередь 2×2 состояние знают **только игровые серверы** — и значит,
опрос, который не смог до них достучаться, обязан сказать «не знаю», а не
«вы в меню». Подробности — в разделе «Она рассчитана на то, чтобы висеть
неделями».

### Форма: Score, ACS, KAST, HS%, K/D, DD

Всё считается из `match-details`, взятого у Riot напрямую, а не с сайта
tracker.gg. `match-history` даёт id последних competitive-матчей игрока,
`match-details` — полный разбор по раундам:

| Колонка | Откуда |
|---|---|
| ACS | `stats.score` / `stats.roundsPlayed` |
| HS% | `roundResults[].playerStats[].damage[]` — `headshots`/`bodyshots`/`legshots` |
| K/D | `stats.kills` / `stats.deaths` |
| DD | (нанесённый урон − полученный) / раунды; урон берётся из тех же `damage[]` по полю `receiver` |
| KAST | раунды, где игрок сделал килл, ассист, выжил или был разменян (окно размена 3 с) |

**Score** — это аналог Tracker Score с tracker.gg. Их число проприетарное:
считается у них на сервере относительно всей популяции игроков, в API Riot его
нет, а Valorant отсутствует в публичном API самого tracker.gg. Поэтому здесь
свой рейтинг **по той же схеме** — те же четыре входа (ACS, KAST, DD, Win%), по
250 баллов каждый, сумма 0–1000.

**С числом на их сайте он не совпадёт и не должен.** Он нужен, чтобы за секунду
отранжировать лобби между собой.

#### Популяция вместо угаданных опорных точек

Сначала счёт считается по фиксированным полосам из `perf.BANDS` — это просто
разумные догадки для платины. Но популяция копится сама: каждый разобранный матч
кладёт в `encounters.db` строки **всех десяти** игроков. Как только наберётся 60
человек хотя бы с 40 раундами каждый, счёт переключается на перцентиль внутри
этой популяции — то есть по той же схеме, что у tracker.gg, только популяция
здесь ваша собственная и потому куда более уместная: это ваш диапазон рангов, а
не весь мир.

`run.bat calibration` показывает, что происходит сейчас:

```
Score calibration  1750 player-lines cached, 76 players with at least 40 rounds
| Metric   | Fixed band 0 / 250 | Your population 25 / 50 / 75 |
| ACS      |          130 / 300 |              184 / 207 / 240 |
| KAST     |            45 / 85 |                 80 / 83 / 87 |
| DD/round |           -40 / 60 |                -21 / -5 / 20 |
| Win%     |            20 / 70 |                 24 / 40 / 60 |
```

Хорошо видно, зачем это нужно: угаданная полоса KAST 45–85 в реальном лобби почти
не работает — живые значения лежат в 80–87, и по фиксированной шкале все получали
бы почти полные 250. Переключение отключается через `"rating_calibration": "fixed"`.

#### Пять матчей — это мало, и таблица об этом говорит

Колонка **N** — сколько матчей стоит за цифрами. Пока их меньше трёх, вся правая
часть строки печатается приглушённо: у человека с одним матчем в истории винрейт
равен 0% или 100%, и это ничего не значит.

Плюс к этому маленькая выборка **подтягивается к середине**, а не принимается на
веру: значение смешивается с нейтральной точкой пропорционально объёму (40 раундов
и 6 матчей — вес нейтрали). Один удачный матч на 30 килов больше не даёт 1000 из
воздуха: та же статистика на 13 раундах даёт ~630, а на полусотне матчей — ~985.

Всё считается **взвешенно**, а не как среднее средних: суммируем score и раунды
по всем матчам и делим один раз. Матч на 25 раундов и матч на 13 не должны иметь
равный вес.

Кэш живёт в `encounters.db` навсегда: результаты матчей неизменны. Причём один
скачанный матч кладёт в базу строки **всех десяти** игроков, а не только того,
ради кого качали. Поэтому холодный старт стоит до ~60 запросов, а дальше цена
лобби быстро падает — на союзников из общих матчей уходит только по одному
запросу истории. `run.bat backfill` разбирает вашу собственную историю заранее,
чтобы первое живое лобби не платило за холодный старт.

Форма берётся из очереди `performance_queue` (по умолчанию competitive). У кого
там пусто — например, играет только анрейтед, — история подтягивается без
фильтра по очереди, иначе половина таблицы была бы из прочерков. Отключается
через `"performance_queue_fallback": false`.

### Сколько запросов уходит наружу

Ники, MMR и история матчей запоминаются на сессию (`player_cache_minutes`).
Это важно из-за перехода agent select → карта: без памяти пять союзников
опрашивались бы дважды подряд, порядка 15 лишних запросов на каждый матч.

Все исходящие запросы идут через один общий тормоз: минимум `request_gap` между
ними, а на ответ 429 — пауза, которую попросил сам Riot (`Retry-After`), после
чего запрос повторяется. Строка под таблицей показывает, сколько запросов реально
ушло — остальное пришло из локального кэша.

Единственное, что стоит дороже одного запроса за раз, — дамп лидерборда для
источника `leaderboard`: 15 страниц по 1000 строк. Поэтому правило для него
намеренно кривое. В живом лобби он читает тот файл, который уже лежит на диске,
каким бы старым тот ни был, и **ни одного запроса не тратит**; перекачивается
дамп после матча или по `run.bat identify leaderboard`, не чаще чем раз в
`leaderboard_cache_hours`.

### Одна таблица на матч

За матч печатается **ровно одна** таблица. Она появляется сразу, как только
виден состав, и дальше обновляется на месте: сначала подставляются ники и ранги,
потом нож, потом форма (это дюжина запросов, поэтому она приходит последней).
Agent select и заход на карту делят один и тот же блок — при старте матча
таблица просто дорастает вражеской половиной, а не печатается заново. Под
таблицей идёт строка состояния (`ранги — 6/10 игроков`), она же в конце
показывает, сколько запросов ушло наружу. Форма отключается через
`"fetch_performance": false`.

Порядок здесь — правило, а не случайность: **сначала на экране вся таблица,
потом в неё доезжают данные**. Всё, что стоит запросов, встаёт на своё место в
уже нарисованной таблице, а не задерживает её появление. Ранг скрытых читается
после того, как таблица показана, и каждый найденный ранг перерисовывает её
сразу, не дожидаясь остальных.

### Шансы сторон под таблицей

Последней строкой — то единственное, чего сама таблица сказать не может:

```
  us 46%   them 54%   39-53% for us across the error
  rank + hidden-MMR pull + form over 5 matches - a lean, not a prediction
  scale is the stated 60/40 prior, not measured yet
```

Десять строк рангов и ACS — это десять фактов про десять человек, а вопрос
перед лобби всегда про две пятёрки. Модель разобрана ниже, в «Шансах на победу»
(ранг + тяга скрытого ММР + форма, переведённая в RR измеренным наклоном), и
запросов она не стоит **ни одного**: всё, из чего она считается,
уже оплачено колонками выше. Поэтому она и стоит последней — ей нужно, чтобы
таблица была дособрана.

Глубина формы написана прямо под числом: `performance_matches` (пять матчей).
Выборка мелкая, и ошибка рядом с числом это показывает — диапазон здесь широкий. В
agent select раздел молчит: одна команда на экране, взвешивать не с чем.
Выключается ключом `"show_odds": false`.

### Кого брать: подсказка в agent select

Под таблицей в agent select печатается короткий список — три агента, по одному
на роль, лучший сверху:

```
Suggested picks  (3 ally agents known, your 214 cached matches)
  1  Omen      Controller  no controller yet, score 619 over 12, 61% here over 9
  2  Breach    Initiator   2nd initiator, score 540 over 7
  3  Iso       Duelist     2nd duelist, nothing cached on them
```

Складывается из двух вещей, и колонка справа всегда говорит, какая из них
сработала:

- **чего не хватает составу.** Роли берутся из данных самого Riot
  (`valorant-api.com` отдаёт `role` у каждого агента), поэтому новый агент
  попадает в нужную корзину сам, без правки таблиц в коде. Дыра в контроллере
  весит больше всех: отсутствие смоков — единственный изъян состава, который
  стабильно проигрывает раунды. Второй инициатор ценится заметно выше второго
  дуэлиста, третий агент роли не даёт почти ничего;
- **как на этом агенте играете вы.** Тот же взвешенный счёт 0-1000, что и в
  таблице, из тех же закэшированных матчей — со сжатием тонкой выборки, поэтому
  один удачный матч на агенте не делает его рекомендацией. Если по вашим матчам
  на этой карте набралось хотя бы три игры, винрейт на ней добавляет или
  снимает до 15 очков.

**По одному агенту на роль — намеренно.** Иначе на пустом кэше все контроллеры
получают одинаковый счёт, и «топ-3» превращается в трёх смокеров подряд по
алфавиту — то есть в один совет, напечатанный трижды. Ограничение по роли
возвращает списку смысл: какую дыру закрывать и кем именно.

Чем список не является: это не мета-подсказка. Никакой таблицы «Viper сильна на
Breeze» в коде нет и не будет — такие таблицы устаревают за патч, а проект и так
построен на том, чтобы считать по вашим данным, а не по угаданным константам.
Карта влияет ровно настолько, насколько вы сами на ней играли.

Пока в кэше нет ваших матчей, работает только первая половина, и подпись это
прямо говорит (`team composition only`). В таком состоянии агент внутри роли
выбирается по алфавиту — сообщать тут нечего, и `nothing cached on them` в
строке об этом честно пишет. Один `run.bat backfill 20` убирает это состояние.

`run.bat agents` показывает ту самую вашу запись, которую читает подсказка:

```
| Agent   | Role       | Matches | Score | ACS | K/D |  WR |
| Omen    | Controller |      12 |   619 | 232 | 1.1 | 58% |
| Sage    | Sentinel   |       7 |   470 | 178 | 0.9 | 43% |
```

Матчи, разобранные до этой версии, агента не хранят и сюда не попадут — они
подтянутся по мере новых матчей или после `run.bat reset` и нового `backfill`.

#### Что это стоит в запросах

Сама подсказка **не ходит в сеть**: роли лежат в суточном кэше справочников,
ваша запись — в локальной базе. Поэтому она появляется на экране сразу, ещё до
того, как подгрузятся ранги.

Платных мест два, оба отключаемые:

- `pregame_refresh` (по умолчанию 5 с) перечитывает agent select, пока он
  открыт, чтобы совет менялся по мере того, как союзники локают агентов. **Один**
  запрос на обновление (id лобби уже известен), и перерисовка только когда
  что-то реально изменилось. За ~75 секунд выбора это порядка 15 запросов;
  `0` выключает, и тогда список считается один раз при входе;
- `recommend_owned_agents_only` — один запрос за сессию к вашим entitlements,
  чтобы не советовать агента, которого у вас нет. Читается только ваш аккаунт.
  Если запрос не прошёл, подсказка просто рассматривает всех агентов.

### Итог матча

Когда матч заканчивается и клиент возвращается в меню, утилита делает **один**
запрос за только что сыгранным матчем — своим собственным — и печатает итоговую
таблицу: счёт по раундам, ACS, K/D/A, KAST, HS% и damage delta каждого, плюс
изменение вашего RR, если Riot уже успел его записать.

Это дёшево вдвойне: тот же ответ кладёт в кэш строки всех десяти игроков.
Он же называет по нику, рангу, RR и пику тех, кто весь матч был `[hidden]`, —
см. ниже.
Отключается через `"post_match_summary": false`.

**Колонка `Hidden MMR` есть и здесь.** Итоговая таблица — единственная, которую
читают *после* матча, а не в спешке перед ним, то есть ровно тогда, когда на
вопрос «куда это всё едет» есть время посмотреть. Стоит она ноль запросов для
того лобби, которое только что отыграли: полосы прочитаны, пока таблица была
живой, и спросить остаётся только про тех, кто прятался, — про них та же
`_reveal` и так делает по запросу на человека.

А в подписи под таблицей рядом с вашим RR за матч встаёт **ваш собственный
потенциал**:

```
+18 RR -> Plat 2 60 RR   hidden rating Plat 3 - Dia 1 (+84 RR of pull)   3 hidden players named once the match ended
```

Два числа рядом не случайно: `+18 RR` — это хороший вечер, а `+18 RR`, когда
система тянет вас на дивизион вниз, — вечер совсем другой, и сказать это может
только пара, а не каждое из них по отдельности.

Матч попадает в записи Riot не в ту же секунду, когда кончается: иногда запрос
за ним какое-то время отвечает «такого матча нет». Это стоило таблицы: несколько
попыток подряд — и матч списывался с сообщением «the finished match was not
published yet - no summary this time».

Теперь матч не теряется **никогда**. Ожидание идёт в три слоя:

1. Пара попыток сразу, пока на экране «match over - reading the result».
2. Дальше — фоновый опрос раз в 10 секунд, пока вы в меню, до
   `summary_wait_seconds` (по умолчанию 180 с). Таблица печатается со всем, что
   знало живое лобби, как только матч появляется.
3. Когда и это время вышло, матч **не выбрасывается**: он записан в
   `encounters.db` (таблица `pending_summaries`) и с этого момента запрашивается
   тихо — раз в 5 минут между матчами и ещё раз при каждом запуске программы.

Третий слой и есть окончательное решение: очередь переживает и следующее лобби,
и закрытие программы, и перезагрузку. Когда матч наконец публикуется, строки всех
десяти игроков уходят в кэш, а таблица печатается — живых строк лобби к тому
времени уже нет, поэтому состав, стороны и агенты восстанавливаются из самой
записи матча, а ники и ранги подставляет тот же механизм раскрытия, что и обычно.

Сдаётся очередь только по сроку: `summary_keep_days` (по умолчанию 7 дней). Riot
бывает медленным, но не неделю — матч старше этого уже не появится никогда.
`"summary_keep_days": 0` — держать вечно, `"summary_wait_seconds": 0` — не ждать
на экране вовсе и сразу отправить матч в очередь.

### В каких именно матчах вы уже виделись

Колонка `Seen` говорит только «сколько раз». `run.bat who <ник>` теперь называет
и сами игры — дату и локальный номер матча:

```
wdfouw#4950  met 5x, 2026-09-02 - 2026-09-08
  score 479  ACS 205  K/D 0.93  KAST 80%  HS 21%  WR 38%  over 8 cached matches
  rank when you met: Silver 2 (2026-09-02) -> Gold 1 (2026-09-08)
  met in (4 of 5 matches): M5 2026-09-06  M4 2026-09-06  M3 2026-09-06  M2 2026-09-06
```

`M4` — номер, выданный этой базой: uuid матча из 36 символов в таблицу не
поставишь. Обратно он разворачивается в то, что можно вбить куда угодно:

```
> run.bat match M4

M4  2026-09-06  Summit  unrated
  match id 7014a334-6be1-40de-a068-ba61849128de
  met here: wdfouw#4950 (5x)  HaraKR#9680 (1x)  byaka#3175 (1x)  ...
```

Связка «игрок — матч» пишется с этой версии при каждом матче. Прошлое
восстанавливается из того, что уже лежит в кэше: в разобранном матче есть строки
всех десяти игроков, значит любой **ваш** матч в кэше — это ещё девять встреч с
датой. Делается это само при `who`, `match` и `backfill`, без сети.

Отсюда и `4 of 5`: пятая встреча была в матче, который в кэш не попал (утилиту
закрыли до конца игры). `run.bat backfill 50` разбирает вашу историю и обычно
закрывает такие дыры разом.

### Карта в заголовке

Заголовок таблицы называет карту: `MATCH LIVE - Ascent - Competitive`. Она же
пишется в базу вместе с каждым разобранным матчем — бесплатно, из того же
`match-details`, который уже скачан ради статистики. На ней и стоит учёт «как
вы играете на этой карте» в подсказке по пикам.

### Ширина окна

Столбцы не обрезаются. Утилита считает нужную ширину и, если окно уже, убирает
наименее полезные колонки целиком — в таком порядке: Knife, Lvl, W/G, Peak, DD,
KAST, N, Seen, HS%, WR, Score, RR, `+/-`, Hidden MMR, Pty. Что скрыто, написано
подписью под таблицей. Team, Agent, Player, Rank, ACS и K/D остаются всегда.
Полный набор помещается примерно в 170 колонок; растяните окно — колонки
вернутся сами при следующей перерисовке.

`Hidden MMR` уходит предпоследней — раньше она уходила четвёртой, сразу за
`W/G`. Это была ошибка по существу: ранг говорит, где человек **стоит**, а
полоса — куда его **тянет**, и второго не повторяет ни одна другая колонка,
тогда как `Peak`, `DD` и `KAST` описывают то же самое с другой стороны.

### Скрытые игроки: `[hidden]` в матче, ник и ранг после матча

Incognito («streamer mode») действует только на **живой** путь поиска — и,
что важнее, только пока матч идёт. Проверено на живых данных, и картина
оказалась не той, что описывалась здесь раньше:

- **`match-details` больше не содержит ников.** `gameName`/`tagLine` приходят
  пустыми у всех десяти игроков, включая вас самих. Раскрытие ников из записи
  матча, которое здесь когда-то работало, тихо перестало что-либо делать;
- **зато `name-service` отвечает про этого же человека, как только матч
  закончился.** Incognito закрывает его ровно на время матча с вами. Один
  запрос на всех, кого не удалось назвать, — и ники есть;
- **`competitiveTier` в записи матча есть у всех**, скрытых в том числе. Это и
  есть тот значок ранга, который tracker.gg рисует рядом с игроком, весь матч
  просидевшим под `[hidden]`.

Граница проходит по концу матча:

- **пока матч идёт** — `[hidden]`, как и раньше. По скрытым игрокам не
  запрашивается ни MMR, ни история; `perf.extract()` читает только `subject`,
  сторону, агента и блоки статистики и полей с именами не касается вовсе;
- **когда матч закончился** — в итоговой таблице у всех настоящий ник, `Rank`,
  `RR` и `Peak`. Ник берётся одним запросом к name-service; как только он есть,
  про этого же человека отвечает и обычный `mmr/v1/players` — то есть текущий
  ранг с очками и пик акта, которых в записи матча нет вообще. Один запрос на
  игрока и только по тем, кого живая таблица не спрашивала: у остальных всё это
  уже прочитано в лобби. Раскрытые ники печатаются голубым, а подпись под
  таблицей называет числа:
  `3 hidden players named once the match ended   3 ranks and peaks looked up after it`.

  `competitiveTier` из записи матча никуда не делся и остаётся запасным
  вариантом: если MMR не ответил, в `Rank` встанет ранг, с которым игрок
  заходил в этот матч, и подпись это скажет — `2 ranks read from the match
  record`. Разница между двумя источниками именно такая: запись говорит, кем он
  был на старте матча, запрос — кто он сейчас.

  Скрытый значок акта уважается и здесь: `IsActRankBadgeHidden` даёт `hidden` в
  колонке `Peak`, как и в живой таблице. Обе новые колонки пропадают целиком,
  если ни у кого их заполнить не удалось, и первыми уходят, если окно узкое.

  Слово `hidden` в этой колонке означает ровно одно — игрок сам спрятал значок
  акта. Ваш собственный `"show_peak_rank": false` не пишет это слово во все
  строки, а убирает колонку целиком, и в живой таблице тоже: настройка вашего
  окна и выбор чужого аккаунта — разные вещи, и выглядеть одинаково они не
  должны. Пик, который просто не успели прочитать, остаётся прочерком.

### Откуда вообще может взяться ник: семь источников

Incognito прячет **имя**, но не идентификатор. `puuid` приходит в любом лобби
независимо от настроек приватности — он есть и у скрытого игрока, и он же лежит
во всех локальных данных. Расшифровать его нельзя: `puuid` не производная от
ника, это просто случайный uuid. Вопрос всегда другой — **записан ли этот puuid
рядом с ником где-то ещё, куда нам и так открыт доступ**.

Мест таких семь, и каждое живёт в `valstats/identity.py` отдельным источником:

| Источник | Что это | Цена | Отвечает во время матча |
|---|---|---|---|
| `memory` | `encounters.db`: вы уже встречали этого человека, когда он не прятался | 0 запросов, работает офлайн | **да** |
| `chat` | `/chat/v5/participants` и `/chat/v4/friends` локального API — там лежат `game_name`/`game_tag` | 0 внешних запросов | **да** |
| `leaderboard` | лидерборд акта: 15 000 строк `puuid` + `gameName`, дамп кэшируется на диск | 15 запросов раз в `leaderboard_cache_hours` | да, но только из уже готового дампа |
| `name-service` | штатный `PUT /name-service/v2/players` | 1 запрос на всех | нет — он и есть то, что Incognito закрывает |
| `match-record` | `gameName`/`tagLine` в `match-details` | 0 запросов | нет |
| `henrik` | `api.henrikdev.xyz`, сторонний индекс `puuid → Riot ID` | 1 запрос на игрока, нужен ключ | да |
| `riot-account` | официальный `account-v1/accounts/by-puuid` | 1 запрос на игрока, нужен dev-ключ | да |

Что из этого проверено на живых данных, а не взято из документации:

- **`chat` действительно не знает про Incognito.** Комната чата во время матча —
  это ваша команда, и участники в ней приходят с ником и тегом. Поэтому скрытый
  **союзник** чаще всего называется прямо по ходу матча и бесплатно;
- **`match-record` сегодня пуст.** `gameName`/`tagLine` приходят пустыми у всех
  десяти игроков, включая вас самих. Источник оставлен, потому что стоит ноль и
  заработает сам, если Riot вернёт поля;
- **`leaderboard` называет примерно три четверти доски.** В последнем дампе eu
  из 15 000 строк именами закрыты 11 579: остальные подняли флаг `IsAnonymized`.
  Такие записи пропускаются — это единственное место, где Riot спрашивает
  игрока про поиск по puuid напрямую, и обходить этот ответ утилита не будет;
- **`name-service` отвечает про скрытого сразу после матча.** Incognito
  закрывает его ровно на время матча с вами;
- **`ShooterGame.log` — тупик.** Ников там нет: в логе лежит уже
  анонимизированное `GameName=Игрок 3` в лобби и `GameName=Reyna` в agent
  select, то есть ровно то же, что видно на экране.

Порядок, в котором источники спрашиваются, задаётся списком `reveal_sources` в
`config.json`. Опрос останавливается **на игроке, а не на источнике**: первый,
кто смог назвать человека, его и называет, остальные про этот puuid уже не
спрашиваются. Поэтому `memory` стоит первым — лобби из знакомых лиц не стоит
ни одного запроса.

Два источника с ключами — `henrik` и `riot-account` — единственное во всей
утилите, что отправляет наружу данные о **другом** игроке. По умолчанию оба
выключены, и включить их мало: нужно и вписать ключ, и добавить имя в
`reveal_sources`. `run.bat test` отдельным шагом печатает, что включено, и
предупреждает про эти два.

### `run.bat identify` — та же машинерия, но вслух

```
run.bat identify              — назвать всех, кого база так и не смогла назвать
run.bat identify <ник|puuid>  — один игрок: что говорит каждый источник
run.bat identify leaderboard  — перекачать дамп лидерборда сейчас
```

Без аргумента — проходит по всем безымянным puuid в `encounters.db`, спрашивает
включённые источники и пишет найденное обратно в базу, чтобы следующее лобби
уже знало:

```
27 players in the local memory have never been named
named 27 of them: 27 from name service
```

С аргументом — наоборот: спрашиваются **все** источники про одного человека, и
ответы печатаются рядом. Смысл именно в расхождениях — ник из `memory`
полугодовой давности и свежий из `name-service` отличаются ровно тогда, когда
аккаунт переименовали:

```
Source             Riot ID        As of
local memory       Nevermore#404  2026-09-06 22:04
client chat        -
name service       Nevermore#404  now
match record       -
act leaderboard    -
```

Если не назвал никто — печатается не ник, а зацепка: с кем этот puuid чаще всего
оказывается на одной стороне. Это не идентификация и ею не притворяется —
просто «через кого тут вообще можно было бы искать». Строится по уже
скачанному кэшу матчей, запросов не стоит.

Источник ника запоминается вместе с самим ником, и `run.bat who` его печатает —
`named by: Nevermore#404 (memory, 2026-09-12)`.

### Что из этого видно в живой таблице

По умолчанию — ничего: `"respect_streamer_mode": true` оставляет `[hidden]` на
месте до конца матча, как и раньше. Это сознательно: пока матч идёт, утилита не
показывает того, что клиент прячет.

`"respect_streamer_mode": false` включает бесплатные источники прямо в лобби —
`memory`, `chat` и уже лежащий на диске дамп лидерборда. Ни одного лишнего
запроса это не стоит и таблицу не тормозит: сеть в живом лобби для этого не
используется вообще. Ник из такого источника печатается с тильдой и
приглушённым — той же пометкой, что и ранг «по памяти», и по той же причине:

```
| ENEMY | Reyna | ~Nevermore#404 | - | ~Immo 1 | ... |
```

`~` означает «так этот puuid звали, когда это в последний раз кто-то записал», а
строка под таблицей называет источники:
`hidden players named: 2 from local memory, 1 from client chat`.
Ник из `chat` тильды не получает — чат отвечает про человека сегодняшнего.

### И в следующий раз — ранг «по памяти»

Всё, что удалось узнать после матча, ложится в локальную базу: ник в
`encounters`, ранг в `rank_snapshots`. Поэтому при **следующей** встрече с тем
же человеком — пусть он снова прячется — в живой таблице вместо прочерка стоит
последний известный ранг, помеченный тильдой и приглушённым цветом:

```
| ENEMY | Phoenix | [hidden] |   - | ~Immo 1  |  - | -      | ... |
```

Это не его сегодняшний ранг, и таблица на это не претендует: `~` означает
«последнее, что мы видели», а строка под таблицей датирует —
`1 hidden player marked ~ carries the last rank we saw them at, from 2026-09-09 or later`.
Стоит это ноль запросов: один локальный SQL по снимкам, которые и так копятся.

### А если мы его видим впервые — ранг из его же матчей

Память помогает только с тем, кого вы уже встречали. Скрытый **незнакомец**
оставался прочерком — в той самой колонке, где прочерк обиднее всего. Между тем
ранг у него есть и лежит там же, где его берёт раскрытие после матча: в записи
любого его сыгранного матча, в поле `competitiveTier`, которое Incognito не
закрывает, потому что Incognito закрывает **запрос**, а не законченный матч.

Теперь живая таблица дочитывает его сама, и читает **ровно столько матчей,
сколько нужно**: история этого игрока, сверху вниз, до первого матча, который
ранг записал. На практике это первый же матч — **два запроса**, и ноль, если
этот матч уже разобран. `rank_hidden_matches` (по умолчанию 5) — это потолок
для того, у кого ранга нет вовсе, а не цена.

Одна деталь тут решает всё остальное: **спрашивается только `competitive`**.
`competitiveTier` заполнен лишь в рейтинговых матчах — в анрейтеде поле есть и
равно нулю (проверено на живом матче: все десять игроков с тиром 0). Поэтому
запасной заход «если рейтинговых нет, возьми любые», который используют
колонки формы, здесь был бы запросами, не способными ответить в принципе. У
человека без рейтинговой истории ранга не найти, и честная цена этого знания —
один запрос, вернувшийся пустым. На живых данных это ровно то, что получилось:
три игрока без рейтинга — три запроса вместо девяти; три игрока с рейтингом —
Gold 2, Gold 1, Gold 1, по два запроса, и ноль при повторной встрече.

Помечается это той же тильдой и той же датой, потому что это то же самое
утверждение: чем он был, когда играл тот матч, а не что ответил бы запрос
сегодня. Ник при этом остаётся скрытым — `respect_streamer_mode` про ник, а
ранг не ник.

Заодно снимки рангов теперь откладывает и обычный сбор формы: пять матчей на
игрока он качает всё равно, а ранги всех десяти в каждом из них до сих пор
выбрасывал. Ноль новых запросов — и следующее лобби со скрытым знакомым уже
ничего не стоит. Выключается ключом `"rank_hidden_from_history": false`.

`run.bat who` находит человека, который в тот вечер играл скрытым, и печатает
трек его ранга по всем встречам. `run.bat backfill` заполняет память задним
числом: проставляет ники всем, кого вы встречали, но видели только как
`[hidden]`, и вычитывает ранги из ваших уже сыгранных матчей. Матчи, разобранные
до появления этой колонки, перечитываются ровно один раз — как это уже сделано
для сторон в пати-детекте.

Выключается одним ключом: `"reveal_after_match": false` — тогда `[hidden]`
остаётся и в итоговой таблице, и ничего из этого в базу не пишется, а значит и
в следующем лобби показывать будет нечего.

Стоит понимать, что именно это меняет в рисках: пока матч идёт, утилита
по-прежнему не показывает того, что клиент прячет. После матча она показывает
то же, что публичная запись матча и любой трекер-сайт. А ранг «по памяти» в
следующем лобби — это не новый запрос про скрытого игрока, а то, что вы уже
узнали законным образом в прошлый раз.

### И вся остальная строка — тоже из его матчей

Ранг был половиной ответа. Вторая половина — это то, ради чего таблицу вообще
открывают: ACS, K/D, HS%, KAST, Score. У скрытого игрока там стояли прочерки, и
это было странно ровно по одной причине: **публичная запись матча отвечает про
кого угодно**. Она и так качается ради формы для всех, кого видно, не спрашивая,
кто из них прячется, — а живая таблица одна во всей программе отказывалась
спросить про остальных.

Теперь спрашивает. Принцип тот же, что и абзацем выше и что везде в этой
программе: **Incognito закрывает запрос, а не законченный матч.** Ник не
спрашивается — сервис имён не трогаем. Ранг «сегодня» не спрашивается — MMR-роут
не трогаем. А история матчей — это другой вопрос, и Riot отвечает на него про
кого угодно: это ровно то, что читают трекер-сайты.

```
| ENEMY | Killjoy | [hidden] | - | Gold 2 | - | - | 540 | 231 | 71% | 24% | 1.20 |
```

Ник по-прежнему `[hidden]`, и `respect_streamer_mode` тут ни при чём — он про
ник. Пустыми остаются ровно те колонки, которые живут **только** в MMR-запросе:
`RR`, `Peak`, `W/G`, `Lvl` и `Hidden MMR`. Их никто не спрашивал и не будет.

Две вещи держат цену честной:

* **порядок.** Пасс идёт **после** того, как заполнена видимая половина
  таблицы. Те пятеро, кого видно, никогда не ждут тех, кого не видно.
* **закрытый роут.** Если Riot уже ответил 401/403 на чужой puuid в предыдущем
  пассе, весь этот пропускается целиком: он провалится одинаково на каждом, по
  запросу на игрока.

Цена в остальном — та же, что у любого другого игрока: `performance_matches`
матчей (по умолчанию 5), и ноль на прогретом кэше. Выключается ключом
`"form_hidden_from_history": false`.

### Заодно — ранг со второго захода, и «Unranked» вместо прочерка

Скачанные матчи несут ранг **всех десяти**, кто в них играл, и `PerformanceFetcher`
их и так складывает в базу. Значит, после этого пасса ранг скрытого игрока уже
лежит локально — и достаётся одним SQL, без единого запроса.

Это не дубль предыдущего абзаца, а второй заход с бо́льшей глубины. Ранг
«из матчей» сдаётся рано и дёшево: `rank_hidden_matches` (5) рейтинговых матчей,
до первого, где ранг записан. Тот, у кого свежие рейтинговые матчи старше этого
окна, возвращался пустым. Более глубокая выкачка, за которую уже заплачено ради
формы, отвечает там, где мелкая не смогла.

И последнее: прочерк в колонке `Rank` означал две разные вещи сразу — «никто нам
не сказал» и «мы посмотрели, и ранга нет». Теперь второе пишется словом:

```
| ENEMY | Reyna | [hidden] | - | Unranked | ... |
```

`Unranked` печатается приглушённо, не жирным: это факт об отсутствии, и он не
должен цеплять взгляд так же, как Radiant. Ставится он **только** когда роут был
открыт и история действительно прочитана: запрос, на который Riot ответил
отказом, не говорит про игрока ничего, и прочерк в этом случае остаётся
прочерком.

### Кто с кем в пати

Колонка `Pty` помечает буквой игроков, которые, судя по всему, зашли в очередь
вместе: `A`, `B` и так далее, своя команда первой. Если в лобби все соло —
колонки просто нет.

`PartyID` Riot отдаёт только по вашей собственной пати, так что группа врагов
восстанавливается косвенно. Люди, которые играют вместе, снова и снова попадают
в одни и те же матчи **за одну сторону** — а эти матчи уже лежат в кэше: они
скачаны ради ACS и формы. Значит, ни одного лишнего запроса: только SQL по
локальной базе.

Три правила держат догадку в рамках:

- Считаются только матчи **за одну команду**. Встреча в качестве соперников не
  значит ничего — это ровно то, что матчмейкер делает со всеми.
- Один общий матч — совпадение, особенно в маленьком регионе, где одни и те же
  лица попадаются регулярно. Порог по умолчанию — два (`party_min_shared`).
- Два матча подряд — **не два свидетельства**. Зайти в очередь вместе — это одно
  решение, которое потом просто повторяют кнопкой Play, так что вечер из пяти
  игр подряд ближе к одному наблюдению, чем к пяти.

Третье правило — главное изменение, и считает его время начала матчей, которое в
кэше уже лежит. Матчи пары разбиваются на **заходы** (sessions): перерыв длиннее
`party_session_gap_hours` (по умолчанию 3 часа) начинает новый. Дальше правило
работает в обе стороны:

- пара вернулась **в другой заход** — это пати. Матчмейкер не сводит одних и тех
  же двоих на одной стороне через день;
- пара просидела вместе **длинную серию внутри одного захода** (четыре матча и
  больше) — тоже пати. Дважды за вечер случайно свести можно, четырежды — нет.

Всё, что перешагнуло порог, но ни одну из этих двух планок не взяло, по-прежнему
показывается — это настоящее свидетельство, — но помечается как тонкое: буква в
таблице получает знак вопроса (`A?`) и рисуется тускло, а в строке под таблицей
появляется `(thin)`. Так с одного взгляда видно, где дуо, а где «может быть».

Группа — это связная компонента таких пар. Она может хватить лишнего: A играл с
B в понедельник, B с C во вторник, а A и C вместе никогда. Тогда все трое
связаны, но не все пары подтверждены — такая группа помечается как `(partly)` в
строке под таблицей и тем же `A?` в колонке, а не выдаётся за уверенную тройку.

Строка под таблицей называет и знаменатель, и разброс по времени:
`A: 2 players, 3 of 5 shared over 3 sessions`. Пара может разделить не больше
матчей, чем закэшировано у того из двоих, у кого их меньше, — «3 из 5» и «3 из
40» читаются очень по-разному; а «4 матча за три вечера» и «4 за один присест» —
это два разных утверждения, и теперь они и написаны по-разному.

Матчи, у которых в кэше не сохранилось времени начала, заходы посчитать не дают
— тогда модуль честно говорит `sessions = 0`, ничего про время не пишет и
откатывается ровно к старому поведению: считает только количество.

### С кем играет конкретный игрок

```
run.bat mates <ник>
```

Списка друзей чужого игрока не существует. Единственный friends-эндпоинт —
локальный, в самом Riot Client, и он отвечает только про аккаунт, под которым вы
вошли; ни официального API, ни стороннего сервиса, который отдал бы чужой
список, нет. Но вопрос, который за этим обычно стоит, — «с кем этот человек
играет» — ответить можно, и ровно теми же данными, что и колонка `Pty`: общие
матчи за одну сторону, разложенные по заходам.

```
                Who toronkills#993 plays with
┌──────────────┬─────────┬──────────┬────────────┬────────┐
│ Player       │ Matches │ Sessions │ Last       │ Party  │
├──────────────┼─────────┼──────────┼────────────┼────────┤
│ you          │      22 │        5 │ 2026-09-12 │ likely │
│ Friend#EUW   │       6 │        4 │ 2026-09-11 │ likely │
│ Kikkii#1021  │       2 │        1 │ 2026-09-12 │ thin   │
└──────────────┴─────────┴──────────┴────────────┴────────┘
```

Те, с кем игрок пересёкся ровно один раз, в таблицу не попадают — это и есть
матчмейкер, и пятнадцать строк случайных людей похоронили бы тех двоих, ради
которых команду и запускали. Их количество печатается строкой под таблицей.

Запросов не делается ни одного, и игра может быть закрыта. Оборотная сторона та
же, что у всей локальной памяти: команда отвечает про ту часть истории игрока,
которая уже есть в кэше, а не про всю. `run.bat backfill` её углубляет.

Имена здесь не читаются вообще: всё считается по puuid, и скрытые игроки
участвуют наравне с остальными. Буква группы — не идентичность, сторону лобби и
так показывает.

Одна оговорка про кэш: матчи, разобранные до появления этой фичи, стороны в
базе не хранят и в расчёт не идут. `run.bat backfill` перечитывает их — один
запрос на матч и только один раз; в его итоговой строке это отдельная цифра
«re-read for sides». Без этого колонка наполнится сама, по мере новых матчей.

## Скрытый рейтинг

Riot не публикует MMR. Зато публикует, сколько RR стоил каждый рейтинговый матч —
а в этом и лежит ответ, потому что система постоянно подтягивает видимый ранг к
скрытому, и тяга видна в перекосе между победой и поражением:

```
+24 за победу, -11 за поражение   система хочет вас выше
+20 за победу, -20 за поражение   вы играете на своём ранге
+16 за победу, -25 за поражение   система хочет вас ниже
```

Оценка — это одно вычитание: среднее за победу плюс среднее за поражение, пополам.
В равновесии выходит ноль. Всё остальное — дрейф за матч, то есть скорость, с
которой ранг идёт туда, где система вас видит. Дрейф превращается в расстояние
через одну константу: дивизион это 100 RR, и при 50% побед система закрывает его
примерно за 20 матчей (`CONVERGENCE_MATCHES` в `mmr.py`). Константа —
калибровка, а не факт от Riot: на выборке из 36 игроков разброс дрейфа дал
стандартное отклонение 2.87 RR, что при этом коэффициенте ставит типичного игрока
чуть дальше полудивизиона от собственного ранга — и сходится со вторым, что та же
выборка говорит: 47% сидят внутри ±1.5 RR от нуля.

**И эта константа больше не только априорная — её мерят по собственному кэшу.**
Модель сервомеханизма говорит не только «дрейф = разрыв / константа», но и что
происходит по ходу подъёма: каждый пройденный RR — это RR, который разрыв
потерял, значит дрейф обязан на столько же упасть. Отсюда сама константа:

```
C = (пройденный путь) / (дрейф в первой половине − дрейф во второй)
```

Обе половины уже лежат в базе. История RR одного игрока, разрезанная пополам,
даёт два дрейфа; ранги, на которых эти матчи игрались, дают пройденный путь.
Ни одного лишнего запроса: это арифметика по строкам, скачанным давно.
Отказывается она чаще, чем отвечает, и каждый отказ — одно из трёх: история
короче 16 читаемых матчей, две половины с одинаковым дрейфом (в знаменателе шум,
делить на него нечего) или частное вне рамок 5–60 матчей — последнее обычно
значит, что игрок за это время вырос и скрытый рейтинг уехал сам, а расчёт
считал его стоящим на месте. Ответ — медиана выживших, и рядом с ней всегда
печатается, сколько историй проголосовало: число, опирающееся на девять игроков,
должно читаться как опирающееся на девять игроков. Смотреть — `run.bat
calibration`, там же, где калибровка оценки 0–1000; переключатель —
`mmr_convergence` (`"auto"` / `"fixed"` / число).

Ответ всегда диапазон, а не ранг. Шум одного матча — около 3 RR, поэтому ширина
полосы считается из стандартной ошибки выборки: шесть матчей дают полосу около
пятой части дивизиона, двадцать пять — вдвое уже. Узкая полоса печатается ярко,
широкая приглушённо: направление стрелки переживает тонкую выборку, а ранги на
концах — нет. **Нулевой ширины не бывает.** Шесть побед, заплативших ровно по
+24, — это маленькая выборка, согласная сама с собой, а не доказательство, что
начисление фиксированное; поэтому к разбросу выборки подмешан априорный шум
матча (`MATCH_NOISE`, 3 RR) с весом в четыре матча — тот же приём, которым
`perf.py` осаживает форму по пяти матчам.

Что выбрасывается перед расчётом — по флагам, которые Riot ставит сам, а не по
догадке «дельта какая-то странная»: `IsPlacementMatch`, `WasDerankProtected`,
`AFKPenalty`, `RRPenalty` (штраф за стак с разрывом в рангах — он уменьшает
начисление по причине, к MMR не относящейся), `RankedRatingRefundApplied` и
выбросы за ±50 RR. `RankedRatingPerformanceBonus` вычитается: он платится за то,
как человек отыграл, а не за то, где система его видит.

**Смена тира больше не выбрасывается скопом.** Раньше любое повышение и любое
понижение считались испорченными: дельта, мол, обрезана границей дивизиона. На
деле обрезается только часть из них, и это не вопрос веры в правила Riot — это
вычитание: ранг до и ранг после лежат в том же ответе, так что пройденный путь
считается напрямую и сверяется с тем, сколько матч, по его собственным словам,
заплатил. Сошлось — ничего не обрезали, матч обычный. Разошлось (упор в пол при
понижении) — выбрасывается, как и раньше. Цена старого правила была не
абстрактной: выбрасывая все повышения, мы выбрасывали победы ровно тех, кого
система тащит вверх, — то есть смещали выборку вниз именно там, где ответ важнее
всего.

**Свежие матчи весят больше.** Разрыв, который мы меряем, — это разрыв
**сейчас**, а сервомеханизм всю выборку его закрывал: вес матча уменьшается
вдвое каждые 12 матчей вглубь. Порядок берётся из времени матча, а не из порядка
в списке, и если времени нет хотя бы у одного — не предполагается ничего,
выборка читается плоско. Веса нормируются **внутри каждой стороны** отдельно:
взвесь победы и поражения по-разному — и середина между ними поедет вслед за
винрейтом, а независимость от винрейта и есть причина, по которой мерят именно
её.

**Полоса говорит, сужается ли разрыв.** Две половины выборки дают два дрейфа, и
`closing` / `steady` / `widening` отличают человека, который
почти доехал до своего ранга, от человека, которого всё ещё несёт.

**Immortal и выше больше не остаются пустыми.** Оценка там по-прежнему не
называет ранг — RR копится дальше 100 против лидерборда, и арифметика «позиция =
тир × 100 + RR» перестаёт что-либо описывать, — но сама тяга измеряется ровно
так же, как у всех: это перекос между двумя начислениями, и к лестнице он
отношения не имеет. В колонке вместо ранга стоит расстояние: `+38 RR ^`.
Раньше эти лобби — те самые, где колонка интереснее всего — были пустыми
целиком.

В живой таблице это одна колонка `Hidden MMR`: зелёным выше ранга, красным ниже,
приглушённым на своём. Стоит один запрос на игрока, выключается `estimate_mmr`.
Та же колонка стоит в итоговой таблице после матча, а ваша собственная полоса —
ещё и строкой под ней, рядом с RR за этот матч.

Две оговорки про то, у кого она спрашивается:

- **скрытых игроков она не трогает**, пока `respect_streamer_mode` включён.
  Ранг «по памяти» в их строке — это то, что вы уже узнали в прошлый раз, и
  стоит он ноль запросов; полоса — это запрос **про них, сейчас, пока они
  прячутся**, а этого живой путь не делает нигде. После матча — делает, там же,
  где спрашивает ник и ранг;
- **закрытый маршрут больше не опустошает колонку.** Riot спрашивается первым,
  потому что история на матч длиннее с каждой игрой, но если он не ответил,
  берутся те же матчи из `encounters.db`. Раньше в этом случае был прочерк —
  при том, что нужные строки лежали на диске.

## Шансы на победу

Единственное под таблицей, что является **моделью, а не фактом**. Поэтому оно и
стоит последним — после строк, а не до них: сначала части, потом сумма, с
которой можно не согласиться. Как это выглядит на экране — выше, в «Шансах
сторон под таблицей»; ниже — из чего это считается.

```
WHO WINS - as far as the cache can tell

  us    Gold 3 77   1477 RR of true rating, 4 of 5 read, 1 taken as the lobby average, give or take 63
  them  Silver 2 93  1093 RR of true rating, 2 of 5 read, 3 taken as the lobby average, give or take 103

  us 83%   them 17%   74-89% for us across the error
  3 of their 5 had no rank anywhere and were taken as the lobby average - this leans on that
  true rating = rank + the hidden-MMR pull + form at 0.44 RR a point (measured on 261 cached players, correlation 0.17)
  scale: one division of difference is 60/40 - a stated prior, not measured
  21 of the 60 cached matches needed to fit one; every sweep from here on adds to that
  the difference is 384 RR, the error on it 121
  what it cannot see: the comps, the map, who is on voice, and whether anybody is trying - a lean, not a prediction
```

У модели три части, и все три названы вслух на экране.

**Что идёт на вход** — одно число на игрока, в RR, «истинный рейтинг»:

```
ранг + тяга скрытого ММР + форма
```

Первое — где человек стоит. Второе — куда его ведёт система, то есть её
собственная поправка к первому, и она **уже измерена в RR** (см. «Скрытый
рейтинг»), складывать её ни с чем не надо. Третье — единственное слагаемое,
которому нужен перевод, и этот перевод **измеряется, а не назначается**: наклон
регрессии ранга на оценку 0–1000 по всем игрокам кэша, у которых есть и то и
другое. На вашей базе это 0.44 RR за очко при корреляции 0.17 — слабая связь, и
наклон именно поэтому пологий: регрессия сама выдаёт правильный вес. Если
корреляция ниже 0.10 или игроков меньше шестидесяти, слагаемое **выбрасывается
целиком**, а не применяется с весом, который ничем не подкреплён.

Игрок без ранга не выбрасывается (иначе «среднее стороны» перестаёт быть средним
стороны). У него **три источника, и они не равны**, поэтому в строке стороны
считаются отдельно:

| источник | откуда | сомнение |
|---|---|---|
| `read` | ранг на руках — спросили сейчас | ширина его полосы скрытого ММР, иначе ±57 RR |
| `from a rank we saw before` | `rank_snapshots`: ранг, на котором мы его видели раньше | ±100 RR |
| `taken as the lobby average` | середина **всего лобби** | ±150 RR |

Средний — это то, чего раньше не было, и на молодом кэше он решает: запомненный
ранг — это наблюдение **про этого человека**, а среднее по лобби — про тех, кто
рядом стоял. Он не выдаётся за сегодняшний (человек с тех пор играл, и куда — мы
не знаем), поэтому сомнения в нём вдвое больше, чем в свежем. В колонку `Rank`
он при этом **не идёт**: таблица фактов обязана говорить либо правду на сейчас,
либо ничего, а модель может взять число постарше, потому что печатает рядом свою
ошибку.

Догадка по лобби, когда и её очередь, берётся не по своей стороне: иначе обе
стороны тихо подтягиваются к тем, кого удалось прочитать. И она **сближает**
стороны, а не разводит, то есть отнимает заявленный перевес, а не выдумывает
его.

**Шкала** — сколько разница в истинном рейтинге стоит в шансах. Одно число,
подгоняемое **методом максимального правдоподобия по вашим же матчам**: берутся
все матчи кэша, где у обеих сторон есть хотя бы по три игрока с рангом и известен
результат. Три причины отказаться, и они важнее самой подгонки: мало матчей;
максимум правдоподобия упёрся в край сетки (это данные говорят «мне нечего
сказать» — ровно так выглядит сезон ровных лобби, и выходить это обязано не
числом); интервал шире, чем удвоенный ответ. Пока подгонки нет — работает
**объявленная априорная шкала**: дивизион разницы это 60/40. Что из двух
использовано, строка под числом говорит каждый раз.

Пока матчей для подгонки мало, это лечится само: проход по истории **сохраняет
ранг каждого из десяти** из того же ответа Riot, который и так скачивается и
раньше выбрасывался. Ноль лишних запросов; старые
матчи ради этого не перекачиваются — ответ, который сам приедет со следующим
проходом, не стоит трёхсот запросов сегодня.

**Ширина.** Вероятность по пяти игрокам — это не три значащие цифры. У каждого
истинного рейтинга есть своя ошибка: ширина его полосы скрытого ММР, если она
есть, иначе — то, что `mmr.py` намерил про типичное расстояние игрока от
собственного ранга (57 RR). Они складываются в ошибку разницы, и та выходит
диапазоном вероятностей, а не одной. Разница внутри 45–55% печатается с подписью
«too close to call»: число всё равно показывается — прятать его хуже, — но читать
его как прочтение нельзя.

Чего модель **намеренно не делает**. Она не подмешивает серию, усталость и флаги:
они настоящие, но сколько стоит серия из четырёх поражений в RR — никто не мерил, и поставить сюда это число значило бы
выдумать самую интересную часть ответа. И она ничего не знает про саму игру:
составы, карта, кто в войсе, старается ли кто-нибудь вообще. 55% здесь означает
«числа клонятся туда», а не «матч решён».

Строка **печатается всегда**, даже когда числа у неё нет. Таблица, под которой
проценты просто не появлялись, выглядела точно так же, как недосчитанная, и
вопрос «а куда делись проценты» задавался чаще всего именно про неё. Одна
строка о том, что двух сторон для взвешивания нет, короче ответа на него.

Цвета постоянные: **мы всегда зелёные, они всегда красные**, куда бы ни склонилось
число. Раньше красился лидер — и тот самый зелёный переезжал со стороны на
сторону между двумя лобби, то есть единственное, что глаз ловит первым, надо
было сначала прочитать. Постоянный код читается взглядом, переезжающий не
читается вовсе.

**Порог — двое размещённых на сторону** (один, если в стороне их всего один-два).
«Размещённый» значит любой из первых двух источников таблицы выше: ранг на руках
или ранг по памяти.

Два прежних правила были ошибкой в одну и ту же сторону — отказывались отвечать
там, где ответ есть, — и каждое по-своему. Тройка была написана, глядя на лобби
5×5, и делала **невыполнимым** любое лобби меньше: матч по двое не даст троих
прочитанных никогда. Половина это чинила и всё равно выбрасывала самый частый
случай: двое противников размещены, трое нет — то есть почти любое лобби на
молодом кэше.

Отвечать здесь безопасно потому, что сомнение уже посчитано: догадка несёт свои
±150 RR, три догадки расширяют полосу так, что это видно, и вдобавок печатается
отдельная жёлтая строка «трое из их пяти взяты по среднему лобби — число
опирается на это». Отказ поверх всего этого был бы вторым отказом за то же
самое. Один размещённый — это по-прежнему ничего: четыре пятых стороны тогда
предположение.

## Она рассчитана на то, чтобы висеть неделями

Смысл утилиты в том, что она **уже запущена**, когда начинается матч. Значит,
единственная по-настоящему серьёзная ошибка — та, после которой нужно идти и
перезапускать окно. Поэтому главный цикл не падает ни от чего, кроме Ctrl+C:

- **любое исключение — это одна неудачная итерация, а не конец программы.** Цикл
  сообщает о ней строкой, паузит (5 с, дальше больше) и продолжает смотреть.
  Пять неудач подряд — и соединение с клиентом пересобирается с нуля, ровно то,
  что раньше делал перезапуск руками;
- **полная трассировка пишется в `errors.log`** рядом со скриптом. Консоль к
  утру пролистается, а файл — нет; если что-то повторяется, там будет видно что
  именно. Файл обрезается, когда дорастает до полумегабайта;
- **токены обновляются заранее.** Riot выдаёт access token примерно на час.
  Раньше он протухал молча, и первый же матч после этого начинался с пачки 401.
  Теперь токен перечитывается на 45-й минуте (один локальный запрос), а 401
  посреди запроса чинится на месте и запрос повторяется;
- **пропажа чата не ослепляет.** Состояние берётся из presence, но чат-сервис
  Riot иногда отваливается, и тогда наш presence просто исчезает из списка —
  раньше утилита в этот момент решала, что игра не запущена, и матч проходил
  мимо. Теперь ещё две минуты после последнего признака жизни состояние
  доспрашивается у `pregame/core-game`;
- **и вранью чата тоже больше не верят.** Presence возвращается после
  переподключения застрявшим на `MENUS` и может просидеть так весь матч: на
  экране — «in menus», таблицы нет, и ничто в этом не похоже на ошибку. Теперь
  каждое `MENUS` раз в `menus_verify` секунд сверяется с `pregame/core-game`,
  расхождение печатается строкой, а дальше до примирения ведут серверы;
- **лобби, которое не прочиталось, больше не списывается вместе с матчем.**
  Восьми быстрых попыток хватает не всегда — длинный экран загрузки, сервер не
  в духе, — а состояние держится следующие сорок минут. Теперь после них
  назначается ещё один заход через 30 секунд, дальше через минуту и так до пяти;
- **«не смог спросить» больше не равно «вы в меню».** Это была самая дорогая
  строчка во всём проекте: опрос `pregame/core-game` начинался с `state =
  "MENUS"` и искал матч, который бы это опроверг, — поэтому **любой** способ не
  получить ответ (протухшая сессия, 429 без попыток, строка билда, которую
  только что обнулил патч) приходил наверх как уверенный факт «человек в меню».
  Исправить это было некому: никто выше не знал, что вопрос остался без ответа.
  Два открытых окна могли просидеть так весь матч, оба со строкой
  «still watching — in menus».

  Больнее всего это бьёт по 2×2, где presence про состояние молчит и опрос —
  единственный источник. Теперь «матча нет» и «ответа нет» — разные возвраты:
  404 это по-прежнему меню, а всё остальное — `None`, то есть «держим последний
  экран, который мы **точно** знали» ещё две минуты, дальше честное «не знаю».
  Заодно неудачный опрос помечает токены как протухшие (самая частая причина —
  именно сессия), так что следующий же `keep_fresh()` чинит это одним локальным
  запросом, и печатает строку — раньше отказ был полностью беззвучным;
- **устаревшая строка билда чинится на месте.** После обновления VALORANT
  Riot начинает отвечать 400 на всё подряд, и наверх это приходит как «матчей
  нет, лобби нет, ничего не происходит» — до самого перезапуска. Первый же 400
  перечитывает билд из `ShooterGame.log` и повторяет запрос. А если и после
  перечитывания 400 остаётся, опрос состояния читает это как «спросить не
  удалось» (`remote(..., strict=True)`), а не как «матча нет» — обычный поиск
  по-прежнему видит `None`, потому что для него ненайденный и неспрошенный
  игрок одинаково непечатаемы;
- **зависание называет себя зависанием.** Отдельный сторож смотрит, как долго
  идёт текущий опрос, и если больше двух минут — печатает строку и сбрасывает
  стеки всех потоков в `errors.log`. Починить он ничего не может, но «висит»
  перестаёт быть неотличимым от «тихий вечер»;
- **и просто отметка о том, что всё живо.** Раз в `heartbeat_minutes` минут в
  меню печатается строка с текущим временем: молчащая программа и намертво
  вставшая оставляют на экране одно и то же — последнюю строку, напечатанную
  час назад;
- **локальный API больше не кидает голых HTTP-ошибок:** любой его отказ — это
  «клиент перезапустили», то есть переподключение, а обрезанный ответ читается
  как «ничего», а не как traceback;
- **справочники перечитываются раз в 6 часов.** Акт сменяется в том числе и
  посреди недельного аптайма, а со старым uuid акта все в лобби внезапно
  становятся Unranked;
- **живая таблица переживает свою собственную поломку.** У `rich` может быть
  только один живой блок; недозакрытый блок раньше ломал все следующие таблицы
  до конца сессии;
- **ник на любом языке печатается, а не роняет процесс.** Riot ID бывает и
  иероглифами; на консоли с ANSI-кодовой страницей это `UnicodeEncodeError` —
  и он повторится в следующем лобби с тем же человеком. Вывод переключается
  в UTF-8 принудительно;
- **сам запуск тоже переживает неудачную минуту.** Если `valorant-api.com` или
  база в этот момент заняты, старт повторяется пять раз с паузой, а не
  заканчивается трейсбеком на первой же секунде.

Что при этом **не** делается: молчание. Каждая перечисленная ситуация печатает
строку — иначе «оно вроде работает» становится неотличимо от «оно висит».

## Что специально сделано «мягко»

- **Streamer mode уважается, пока идёт матч.** Игрок с `Incognito`, либо тот,
  чьё имя name-service вернул пустым, показывается как `[hidden]`, и по нему не
  запрашивается ни MMR, ни история матчей. Единственное, что может стоять в его
  строке, — ранг, и только если он уже лежит в локальной памяти с прошлой
  встречи (помечен `~`). После матча итоговая таблица называет всех по нику,
  текущему рангу и пику — так же, как это делает трекер-сайт (см. выше;
  отключается `"reveal_after_match": false`).
- **Скрытый значок ранга акта уважается.** Если у игрока стоит
  `IsActRankBadgeHidden`, в колонке Peak будет `hidden` — и только в этом
  случае: `"show_peak_rank": false` просто убирает колонку.
- **Никакого оверлея поверх игры.** Обычное окно консоли. Оверлеи с подсказками
  в реальном времени — отдельный и куда более жёсткий пункт правил Riot.
- **Никакого автолока агента и вообще никаких действий в игре.** Утилита только
  читает; ни одного запроса, который что-то меняет.
- **Пауза 150 мс между запросами**, чтобы не ловить 429.

исключение занятых и недоступных агентов, влияние своей записи и карты,
по одному агенту на роль, устойчивый порядок при равенстве), группировка своих
матчей по агентам и картам, разбор метаданных матча, раскрытие ников и рангов
после матча (и что оно не трогает живую таблицу), запрос к name-service вместо
опустевшей записи матча, ранг «по памяти» для скрытого игрока и однократный
перечит старых матчей ради него, а также устойчивость: коды ответа
локального API, обновление токенов по возрасту, пропажа presence и запасной
опрос, presence, застрявший на `MENUS`, и возвращение доверия к нему, повтор
запроса на свежей строке билда после 400, отложенный заход на лобби, которое не
прочиталось, отметка «всё живо», переживание ошибки в тике и пересборка
соединения, поломанный живой блок `rich`. Игра и сеть не нужны.

## Риск бана — читайте

Это **не чит**: Vanguard такое не детектит, потому что детектить нечего —
процесс не касается игры. Но правила Riot про сторонние приложения нарушаются
всё равно, по другой причине: **утилита показывает информацию, которую клиент
специально скрывает** — ранги и статистику соперников до и во время матча.
Политика Riot требует, чтобы данные игрока показывались третьим лицам только
после его явного согласия через RSO.

Что известно по фактам:

- Есть подтверждённые репорты банов с формулировкой *«external program that
  reveals hidden information»* — например
  [issue #290 в vRY](https://github.com/zayKenyon/VALORANT-rank-yoinker/issues/290)
  (июнь 2026).
- Сам vRY выпустил финальный релиз и закрылся, организация на GitHub
  заархивирована в 2026 году.
- Recon Bolt получил от Riot cease and desist в июле 2023 и был закрыт.
- Массовых банвейвов именно за трекеры не было — заносят точечно, вручную.

Отдельно про источники ника. `memory`, `chat`, `name-service` и `match-record`
отвечают тому же клиенту и той же авторизации, что и сама игра; `leaderboard` —
публичная доска, которую Riot отдаёт кому угодно. А вот `henrik` и
`riot-account` — другое дело: первый отправляет чужой puuid стороннему сервису,
второй требует dev-ключ, выданный на условиях, которые стоит прочитать прежде,
чем наводить его на посторонних. Поэтому оба выключены по умолчанию, и включать
их — отдельное осознанное решение, а не галочка.

Смягчения выше (streamer mode, отсутствие оверлея, только чтение) снижают риск,
но **не убирают его**. Если хотите нулевой риск — поставьте
`"respect_streamer_mode": true` и смотрите только свою статистику, либо
пользуйтесь официальным приложением tracker.gg через Overwolf.

Тестируйте на том аккаунте, который не жалко.

## Ограничения

- Определение групп работает по кэшу и потому неполно: пати, у которой в базе
  нет двух общих матчей, не видна. Riot по чужим игрокам `PartyID` не отдаёт, и
  спрашивать его неоткуда.
- Списка друзей чужого игрока не существует ни в каком виде: единственный
  friends-эндпоинт — локальный, в Riot Client, и отвечает только про тот
  аккаунт, под которым вы вошли. `run.bat mates` отвечает на вопрос, который за
  этим обычно стоит — с кем человек реально ходит в очередь, — но по своему
  кэшу, а не по всей его истории.
- В agent select в соревновательном режиме видна только своя команда — это
  ограничение самого API, а не утилиты. Полный состав появляется при заходе на
  карту. По той же причине подсказка по пикам считает состав только своей
  команды: чем контрить врага, она сказать не может.
- Только Windows: пути к lockfile и логам захардкожены под неё.

## Структура

```
valstats/client.py    lockfile, токены, регион, HTTP к local/pd/glz, пейсинг, память
valstats/content.py   справочники valorant-api.com + кэш на диске
valstats/config.py    умолчания и проверка config.json
valstats/stats.py     разбор pregame/coregame/MMR в строки таблицы
valstats/perf.py      форма из match-history + match-details, рейтинг, калибровка
valstats/picks.py     подсказка по агентам: дыры в составе + ваша запись
valstats/party.py     кто с кем в пати: общие матчи за одну сторону, разбитые по заходам
valstats/mmr.py       скрытый рейтинг из перекоса начислений RR, полосой с ошибкой
valstats/conduct.py   AFK-раунды, тиммкилл, штрафы и длина сессии из записи матча
valstats/odds.py      шансы сторон: истинный рейтинг в RR, шкала по кэшу, диапазон
valstats/identity.py  семь источников ника по puuid и порядок их опроса
valstats/identify.py  команда identify: те же источники, но вслух и по одному
valstats/db.py        SQLite: встречи (и в каких матчах), ранги, агенты, карты, популяция
valstats/render.py    живая таблица и итоговая таблица матча
valstats/app.py       главный цикл: presence -> состояние -> экран -> итог
valstats/history.py   команды who / mates / match / top / backfill / agents / calibration
valstats/selftest.py  диагностика цепочки без матча
tests/test_stats.py   офлайн-проверки
```

Не связано с Riot Games. Используйте на свой риск.
